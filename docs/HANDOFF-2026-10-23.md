# heat-governor handoff (2026-10-23)

Written from a lobes-cli session before a context compaction. The repo today is the agent scaffold only
(CLI, identity, CI); no thermal code yet. Read this, then the repo's own `CLAUDE.md`, before building.

## What the operator decided

- **Language: Python** (the existing 3.12 scaffold), supporting **DGX Spark (GB10), Jetson AGX Thor and Jetson AGX
  Orin**. A later Go daemon was suggested in outside advice; not decided, do not start it.
- **Goal:** keep machines running heavy AI work **without hard resets** while losing as little effectiveness as
  possible ("I don't want resets, but I also don't want to lower machine effectiveness").
- **Build the adaptive GPU-work limiting discussed below** (proportional duty-cycle throttling for side jobs, load-side
  adaptive concurrency for serving lanes), plus the CPU caps and telemetry that already exist in lobes.
- The GPU clock cap (`nvidia-smi -lgc`) was parked, then **opened by the operator** later the same day:
  a root helper with a narrow sudoers rule is installed on all four boxes; `lock` at the maximum clock
  was accepted on GB10 and both Jetsons. What a lower ceiling does is not yet measured.

## What we measured on the Spark (GB10) on 2026-10-23

- **Two silent hard resets** (07:11:13Z, ~08:56:40Z): no shutdown, no kernel log; the journal just stops. Both during
  long-context LLM decode (130k+ token contexts). The earlier 2026-10-14 resets were during GPTQ quantization.
- **The hot sensor is an ACPI zone, not the GPU.** At the first reset: GPU 79-82 C, ~75 W, ~2.2 GHz (max is 3 GHz),
  while the hottest ACPI zone sat at 94-96 C; one SW thermal slowdown event (`0x20`) 30 s before power-off.
- **Thermal zones:** 7 `acpitz` zones (`/sys/class/thermal/thermal_zone0..6`), every trip point at 104.8 C; zones 0
  and 4 run hottest. hwmon: acpitz, nvme, mt7925 (wifi). The reset happens around **94.5-95 C**, well under the trip.
- **Zone 0 is fast:** it jumped 91.8 -> 96.5 C in 2 s with the GPU flat at 77 C / 54 W / 2424 MHz, and fell to 83 C
  within 2 s of a pause. Looks like a board/SoC hotspot or power-related, not heatsink mass.
- **A 3 s poll overshoots** a 92 C pause by up to 4.5 C; a 1 s poll lands pauses at 92.0-94.8 C (median 92.3).
- **CPU caps (`docker update --cpus`) barely affect GPU-driven heat:** at 4 CPUs the zone still went 87 -> 95 C in
  ~12 s after each resume.
- **What held** (a 3 h 28 min long-context window, then a second model's window, no reset): one request at a time (two for the second model), governor
  pause 92 C / resume 86 C, 1 s poll, CPU bands 85:12,88:8,90:4 with a gradual ramp, nothing else on the GPU.
  Cost: ~6% of time paused (45 pauses in 32 min), plus the lower concurrency.
- **Controls the OS shows on GB10:** `nvidia-smi` reports `Supported Clocks: N/A` and every power-limit field `N/A`;
  the `spark window lock` (clock lock) tool returns `unsupported`. Fans are firmware-controlled (no OS control
  seen). Outside reports say root `nvidia-smi -lgc` may work on GB10 — untested here, parked.
- No sudo for us on the Spark beyond a `drop_caches` rule; the user is in the `docker` group.

## The two adaptive mechanisms to build

1. **Proportional duty-cycle throttling (side containers / batch jobs).** Instead of bang-bang pause at 92 C, pause
   for a fraction of each second that grows with temperature (e.g. 0% < 86 C, ~10% at 88, ~30% at 90, ~60% at 92,
   full pause at a hard limit). A frozen process issues no new GPU kernels (decode steps are ~10-30 ms), so GPU
   load and heat fall in proportion. Non-root path: `docker pause` / `docker unpause` (cgroup freezer); measure the
   CLI latency per call first — it bounds the usable rhythm. Include the temperature's rate of change (zone 0 moves
   2-5 C/s). Never pause a container the governor did not pause (keep the own-pause rule).
2. **Load-side admission / adaptive concurrency (serving lanes).** Serving lanes (lobes `cortex` etc.) must never be
   paused (lobes rule). Instead expose a signal clients read (e.g. a state file or tiny HTTP endpoint: cool / warm /
   hot) so a benchmark or batch client lowers its concurrency or holds new work. The lobes gateway already sheds
   full tiers at 98 C (`LOBES_THERMAL_SHED_C=98`, resume 94) — too high for the measured ~95 C reset point.

## Design principles (operator + advice, compatible with ours)

- Separate **policy** (pure, testable, ~1 Hz feedback: temperature, rate of change, hysteresis, dwell times) from
  **adapters** that advertise what they can read and safely change per platform.
- Separate **learning from enforcing**: record every run (temps, clocks, throughput, control actions, resets) and
  propose better profiles; never auto-deploy newly learned limits without validation.
- Conservative fallback; never depend on an LLM or the network to keep governing; keep NVIDIA's own protections.
- Fail safe on sensor loss (treat a missing reading as hot, not cool) and on crash (release only its own pauses).

## Suggested first milestones

1. Read-only `sense` + `capabilities` per platform (Spark, Thor, Orin), with fixtures from real sysfs captures.
2. Recorder (port log2.py) with boot markers and a reset report (`last N seconds before the gap`).
3. Pure controller: CPU bands + ramp (port), PWM duty mapping with rate-of-change term, unit tests on recorded traces
   from today (the 1 s telemetry log of 2026-10-23 and the governor logs of that day's windows).
4. Actuators: docker cpus, docker pause duty-cycle (own-pause rule), admission signal for clients.
5. Live validation on a side-container window on the Spark, with nothing else on the GPU; measure duty vs peak
   temperature vs throughput against today's bang-bang baseline.

## Do not

- Run heavy GPU tests on either Spark while the operator's long benchmark run is going.
- Pause or docker-update a serving lane without the operator saying so.
