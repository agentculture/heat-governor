### t2 — memprocs.py: /proc process scan (anon RSS, uid, parent chain, start time, cgroup), growth, grouping, top-N, redaction

## Wave 2

### t6 — memkill.py: victim choice, pidfd-pinned SIGKILL, protect list, kill budget, repeat offenders

- instruction: New module `heat_governor`/memkill.py using memprocs. choose(): own uid only; the biggest anon grower >= `min_victim_mib` not protected (pid 1, the daemon and its parent chain, systemd, sshd, gnome-shell, Xwayland, tailscaled, dockerd, containerd, plus config protect); if none qualifies, the fastest-growing group's biggest member (decision c37). kill(): os.`pidfd_open`, re-check start time and uid via /proc, signal.`pidfd_send_signal`(SIGKILL); both callables injected. Budget: `max_kills_per_hour` rolling; past it -> would-kill + `memory_budget_exhausted`. Repeat key (uid, exe, sha256(cmdline)) within 30 min -> repeat N. Returns event dicts; writes nothing itself.
- covers: c4, h10, c30, h24, c32, h26, c33, h27, c17, h21
- acceptance:
  - tests/`test_memkill.py`: other-uid, protected, self, parent-chain and under-minimum processes are never chosen; with no single eligible process, the biggest member of the fastest-growing group is chosen
  - a pid whose start time changed between scan and kill is not signalled; the kill goes through the injected `pidfd_send_signal` with SIGKILL
  - the 4th trigger within an hour returns would-kill plus `memory_budget_exhausted` and sends no signal; three kills of the same cmdline in 30 min carry repeat 1, 2, 3
  - one test spawns a real 'sleep 60' child of the test process (own uid) and confirms the real pidfd path kills only it

## Wave 3

### t8 — memguard.py: the guard thread (poll, trigger, kill, OOM counters, top snapshots, mlockall)

- instruction: New module `heat_governor`/memguard.py: MemGuard(rule, `proc_root`, `sys_root`, clock, kill, emit, mlockall).start() runs its own thread polling /proc/meminfo every rule.`poll_s`; Trigger (t1) decides; on fire, memkill (t6) chooses and kills (action=kill) or records `memory_would_kill` (action=record). Each poll reads /proc/vmstat `oom_kill` and memory.events of user.slice/user-1000.slice and the daemon's delegated cgroups; deltas emit `oom_kill` events. Emits top snapshots every `top_every_s`, every poll while avail < `soft_pct`. doc() returns the `mem_guard` state object {action, armed, `avail_mib`, `last_kill`{t,pid,comm,`rss_mib`,repeat}, `kills_last_hour`}. Best-effort mlockall(`MCL_CURRENT`|`MCL_FUTURE`) via ctypes when action=kill; result logged. emit() is the only output.
- covers: c2, h8, c7, h12, c14, h19
- acceptance:
  - tests/`test_memguard.py`: with a fake meminfo falling at 1.2 GB/s the guard fires and the injected kill is called before avail < 2048 MiB; with action=record it emits `memory_would_kill` and never calls kill
  - while a fake tick thread sleeps 30 s holding no shared lock, guard polls continue every `poll_s` (measured with a fake clock / counter)
  - stepping fake `oom_kill` and memory.events counters emits exactly one `oom_kill` event per delta
  - mlockall refused (fake returns -1) is logged and the guard still runs; doc() shape matches the state.md `mem_guard` row

## End state

### Announcement

- heat-governor catches a runaway process before it takes the machine down: when memory is about to run out it kills the biggest own-user grower, records who used the memory and what started it, and keeps that record in S3 so a dead machine's last minutes survive off-box.

### After state

- After: a runaway own-user process is SIGKILLed before available memory reaches zero; the box stays up and responsive; the records name the process, its growth, its parent chain and the moment of the kill; and the same evidence plus a rolling black box is in S3 within seconds, readable with 'heat-governor ship fetch' from any machine even if the box never comes back.

### Success signals

- In a controlled test on the EliteMini, a process allocating 1.2 GB/s is killed with available memory still >= 2 GB, the governor records no tick gap > 2 s during the run, and the memory_kill event is in S3 within 10 s of the kill.
- Replaying the 2026-11-14 records through the trigger fires on every one of the five waves at least 15 s before available memory fell below 2 GB, and fires 0 times across the 2026-11-10..13 records (no false kills on a normal week).
